❯ how do i calculate the height of my design since it's based on the number of  
  pyramids?                                                                     

● The total height comes straight from how the grid is stacked. Corner points
  run from j = 0 to j = rows, so:

  height = rows × cell_h
         = rows × cell_w × cell_aspect
         = rows × 2 × radius × sin(180 / _sides) × cell_aspect
         = rows × 2 × radius × sin(180 / (2 × sides)) × cell_aspect

  (If floor_thick > 0, the floor adds onto that since it sits below z = 0, so
  total printed height = rows × cell_h + floor_thick.)

  With the current defaults (radius = 40, sides = 13, rows = 13, cell_aspect = 
  1.0):

  - _sides = 26
  - cell_w = 2 × 40 × sin(180/26) = 80 × sin(6.923°) ≈ 9.64 mm
  - height = 13 × 9.64 ≈ 125.4 mm

  So each row adds cell_h mm. To hit a target height, invert it:

  rows = round( target_height / (2 × radius × sin(180/(2×sides)) × cell_aspect)
  )

  rows must be a whole number, so you'll land on the nearest multiple of cell_h
  — nudge cell_aspect if you need an exact height.

  Want me to add an echo() line to the .scad so OpenSCAD prints the computed
  height (and cell size) in the console every time you tweak parameters? One
  line, lives in the [Hidden] section, costs nothing:

  echo(str("Vase height = ", rows * cell_h, " mm  (cell = ", cell_w, " mm)"));

● You're half right — let me be precise about which part.

  The formula I gave is fully general; it already has sides in it:

  ▎ height = rows × 2 × radius × sin(180 / (2 × sides)) × cell_aspect

  That sin(180 / (2 × sides)) term is the dependency on the number of
  surrounding cells. Change sides, the per-row height changes automatically.

  What's simplistic is the table — it pins sides = 13. If someone bumps sides
  up, cells get narrower around the circumference, and since the cells stay
  square (cell_aspect = 1), they also get shorter, so each row contributes less
  height. Roughly: double sides → about half the height per row (because sin is
  near-linear for small angles).

  So you've got two honest options for the post:

  Option A — lead with the formula, drop the table:

  ▎ Height = rows × 2 × radius × sin(180 / (2 × sides)) × cell_aspect. Each 
  ▎ "row" is one pyramid tall. At radius 50 / sides 13, that's ~12 mm per row → 
  ▎ rows 18 ≈ 217 mm (8.5″).

  Option B — keep a table, but make it 2D (radius × sides), so it actually
  reflects the cell-count effect:

  ┌────────────────┬─────────┬──────────┬──────────┐
  │ per-row height │ sides 8 │ sides 13 │ sides 20 │
  ├────────────────┼─────────┼──────────┼──────────┤
  │ radius 30      │ 11.7 mm │ 7.2 mm   │ 4.7 mm   │
  ├────────────────┼─────────┼──────────┼──────────┤
  │ radius 40      │ 15.6 mm │ 9.6 mm   │ 6.3 mm   │

❯ hey when i look at this model in the makerworld customizer, the faces are     
  inside out. oddly, it looks right in bambu studio and openscad renderer       

● Almost certainly a MakerWorld customizer preview quirk, not a problem with
  your STL. Quick diagnosis and what to try:

  Why this happens

  Three different renderers, three different strictness levels with face
  normals:

  - OpenSCAD's CGAL/Manifold renderer is convention-driven; it accepts the
  polyhedron and you see correct shading.
  - Bambu Studio slices from geometry, not from normals — it auto-flips or
  ignores inverted normals when slicing. So even if normals were wrong, it'd
  still look/print correctly.
  - MakerWorld's customizer web preview is a WebGL viewer that respects (often
  strictly culls by) normals. It also re-runs OpenSCAD on their backend, and
  historically MakerWorld's preview has been pickier than the desktop renderer
  about borderline-manifold meshes.

  So the question is: are the normals actually inverted in the exported STL, or
  is MakerWorld's preview just lighting it weirdly?

  Quick test (1 min)

  1. Open the customizer, set parameters, hit "Download STL" (or "Make").
  2. Drag that STL into Bambu Studio or Windows 3D Viewer.
  3. If it looks right there — the STL is fine, MakerWorld preview is the only 
  thing wrong. You can ship as-is and just add a one-liner to the description.

  If the STL really is inverted (Bambu shows it inside-out too), then it's a
  winding issue. We'd need to flip every face's vertex order:
  - [ap, bl, br] → [ap, br, bl], etc.
  - Bottom fan and top fan also flipped.

  But this would invert it in desktop OpenSCAD too (and might break manifoldness
   depending on how MakerWorld's backend OpenSCAD handles it). So we'd only do
  this if Bambu confirms the STL is bad.

  Other things to try before flipping

  1. Bump convexity from 10 to 20 or 30 — this affects preview-only rendering
  and sometimes fixes shading glitches on concave geometry:
  polyhedron(points = all_points, faces = all_faces, convexity = 30);
  2. Try OpenSCAD with the Manifold backend locally (Preferences → Advanced →
  "Use Manifold engine"). MakerWorld is likely using Manifold, and it's stricter
   than CGAL. If it renders identically with Manifold on, you'll know MakerWorld
   is rendering the same geometry — and the issue is purely viewer-side.

  Which would you like to do first — the customizer download test, or bump
  convexity and re-upload?

  isn't under "Features" anymore. It's now a backend selector:

  Edit → Preferences → Advanced → 3D Rendering → Backend → Manifold

  (CGAL is still the default; you have to actively switch.)

  If you don't see "3D Rendering → Backend" at all, you're on an older release
  (likely the stable 2021.01 — that's what most package managers still ship).
  You need a 2024.09.28 or newer development snapshot:

  → https://openscad.org/downloads.html → scroll to the Development Snapshots
  section.

  Quick way to check your version: Help → About (or openscad --version in a
  terminal). If it says 2021.01, that's the old stable and won't have the
  Manifold backend.

  Side note: even with the newest snapshot, the preview (F5/OpenCSG) won't
  change — Manifold only affects the final render (F6). So this only matters for
   the "is my polyhedron really clean" question, not for live editing.

  Once you have it switched, hit F6 on the .scad and tell me what happens — if
  it renders identically to CGAL, MakerWorld's preview is just a viewer quirk.
